# kubejs-dupes — поиск циклических дюпов в рецептах KubeJS-сборки

Утилита находит в экспорте рецептов Minecraft-сборки **замкнутые цепочки с профитом**:
комбинации рецептов, которые превращают одну единицу ресурса в большее количество той же
единицы, не требуя ничего извне. Именно такие циклы ломают баланс: например,
слиток → 3 пластины → 270 mB → 3 слитка.

Работает офлайн: игру не запускает, моды не загружает — читает только папку экспорта,
которую создаёт сам KubeJS.

## Требования

* **Python 3.8+** — больше ничего ставить не нужно, код на стандартной библиотеке.
* **Экспорт рецептов KubeJS** — папка `export`, полученная из игры (как её сделать — ниже).
* Опционально **scipy** (`pip install scipy`) — только для проверки полноты `--prove`.

Отлажено на KubeJS 2101.7 (NeoForge 1.21.1). Структура экспорта в других версиях KubeJS
может отличаться: утилита читает `recipes/`, `tags/` и `registries/` и просто пропускает
всё, чего нет.

## Как получить экспорт

1. Запустите сборку с KubeJS (в одиночной игре серверная часть стартует вместе с клиентом).
2. Выполните команду с правами оператора (в одиночной игре — включённые читы):

   ```
   /kubejs export debug
   ```

   Алиас команды — `/kjs export debug`. Голый `/kubejs export` ничего не выгружает: он
   только перечисляет подкоманды (`debug`, `pack-zips`, `pack-folders`,
   `recipe-schema-json`), данные пишет именно `debug`. Сервер после команды перезагрузится,
   а в чат придёт `Done! Export in local/kubejs/export`.
3. Папка появится в `<game dir>/local/kubejs/export`: у клиента это
   `<инстанс>/.minecraft/local/kubejs/export`, у сервера — `<папка сервера>/local/kubejs/export`
   (путь задан в KubeJS как `GAMEDIR/local/kubejs/export`, лаунчер на него не влияет).
4. Каждый экспорт перезаписывает папку и удаляет файлы, которых больше нет. Кэш утилиты
   привязан к `export/recipes`, так что после нового экспорта следующий прогон будет холодным.

Удобно держать копию экспорта рядом с репозиторием — в папке `export/` (она в `.gitignore`):
тогда тесты находят данные сами, а `--export export` короче, чем путь к инстансу.

Что утилита берёт из экспорта:

| путь | обязательно | зачем |
|---|---|---|
| `recipes/**/*.json` | да | сами рецепты |
| `tags/<datapack>/<registry>/<ns>/<path>.json` | да | разворачивание тегов (`#c:ingots/steel` → реальные предметы) |
| `registries/item.json`, `registries/fluid.json` | нет | точнее различать предмет и жидкость с одинаковым id |
| `errors.log` | нет | рецепты, которые игра не загрузила, исключаются из анализа |

`added_recipes/` и `removed_recipes/` не читаются: первые — побайтовые копии `recipes/`,
вторые — *старые* версии рецептов до KubeJS.

## Быстрый старт

Из корня репозитория (там, где лежит папка `kubejs_dupes/`):

```bash
python -m kubejs_dupes --export /путь/к/export
```

Windows (путь с пробелами — в кавычках):

```bat
python -m kubejs_dupes --export "D:\instances\MyPack\.minecraft\local\kubejs\export"
```

Отчёты по умолчанию складываются в `out/` рядом с кодом, другая папка — `--out`.

Полезные варианты:

```bash
# подписать отчёт именем сборки и проверить полноту через LP
python -m kubejs_dupes --export /путь/к/export --pack "My Pack" --prove

# искать циклы до 5 шагов (дороже) и расписать все находки, а не первые 60
python -m kubejs_dupes --export /путь/к/export --depth 5 --top 0

# строгий режим: не учитывать шансы < 100 % и не подставлять произвольных членов тега
python -m kubejs_dupes --export /путь/к/export --chance strict --tags primary
```

## Ключи

| ключ | по умолчанию | смысл |
|---|---|---|
| `--export PATH` | — | папка экспорта KubeJS (обязательный) |
| `--out DIR` | `<repo>/out` | куда писать отчёты и кэш (`<out>/cache`) |
| `--pack NAME` | — | имя сборки для заголовка `dupes.md` |
| `--depth N` | `4` | максимум шагов в цикле (2–6); 5 заметно дороже |
| `--min-profit X` | `1.02` | минимальный множитель, при котором цикл считается дюпом |
| `--max-verify N` | `50000` | сколько кандидатов доводить до точной проверки |
| `--tags node\|primary` | `node` | `node` — тег может дать любого члена; `primary` — только канонический |
| `--chance expected\|strict` | `expected` | `expected` — выход умножается на шанс; `strict` — только 100 %-ные выходы |
| `--max-edges N` | `0` | лимит исходящих рёбер на ресурс (0 — без лимита, рекомендуется) |
| `--top N` | `60` | сколько дюпов расписать подробно (0 — все; сводка всегда полная) |
| `--no-collapse` | выкл. | не сворачивать варианты того же дюпа (обвязка 1:1, развёрнутый шаг, склейка) |
| `--prove` | выкл. | LP-проверка «других дюпов нет» (нужен scipy) |
| `--no-cache` | выкл. | игнорировать кэш нормализации |

## Что на выходе

| файл | содержимое |
|---|---|
| `out/dupes.md` | главный отчёт: сводная таблица и по каждому дюпу таблица шагов (вход → выход, тип рецепта, число крафтов) + альтернативные рецепты + раздел свёрнутых вариантов |
| `out/dupes.json` | то же машинно-читаемо; свёрнутые варианты — в `redundant.closed` / `redundant.open` со ссылкой `core` на номер ядра |
| `out/open_cycles.md` | циклы с профитом, которым не хватает внешнего ресурса |
| `out/coverage.md` | статистика парсера по типам рецептов: что разобрано, что выпало |
| `out/prove.md` | результат LP-проверки (появляется с `--prove`) |
| `out/cache/` | кэш нормализации: повторный запуск не перечитывает десятки тысяч файлов |

## Как читать отчёт

Каждый дюп — таблица, строка на шаг цикла. **Жирным** — ресурсы, которые реально
циркулируют в цикле; обычным — привнесённые извне. `Машина` — сырой `type` рецепта из
экспорта (переводов нет: в данных есть только он). `(тег …)` — рецепт принимает любой
предмет этого тега, в цикле используется указанный. `Крафтов` — сколько раз запустить
рецепт за один прогон; партия подбирается так, чтобы все количества были целыми.

Под таблицей: `не тратится:` — формы литья, молды, инструменты (катализаторы, они не
расходуются); `рецепты:` — точные id для отчёта авторам сборки; `альтернативные рецепты
(тот же коэффициент):` — другие рецепты той же пары ресурсов с тем же коэффициентом
(например `packer` и `craft` для 9 пылинок → 1 пыль).

Один и тот же дюп можно «удлинить», не добавив ничего нового. Все три случая сворачиваются
в ядро, а вариант уходит в раздел «Свёрнутые дубли» с причиной:

* **обвязка 1:1** — набор рецептов короткого цикла строго вложен в длинный при точно равном
  профите: `unpacker/nugget/zinc` + `packer/ingot/zinc` (слиток ⇄ 9 самородков),
  `crusher/coal` + `compressor/coal` (уголь ⇄ угольная пыль);
* **развёрнутый шаг** — шаг ядра заменён путём между теми же ресурсами с тем же
  произведением коэффициентов (`ingot → plate → dust` вместо `ingot → dust`): наборы
  рецептов не вложены, поэтому сверка идёт по узлам, а не по множеству id;
* **склейка** — длинный цикл это два других дюпа подряд: набор = A ∪ B,
  профит = профит A × профит B.

## Как это работает

1. **Загрузка.** Читается только `recipes/`. Рецепты из `errors.log` (не прошли валидацию
   в игре) отбрасываются, как и мусорные выходы (`*jei_dummy*`, `*:air`).
2. **Нормализация.** Несколько сотен типов рецептов приводятся к единому виду
   `Recipe{ins: {ресурс: количество}, outs: …}`: общий рекурсивный парсер + словари ключей
   (`ingredient(s)`, `input`, `item_result`, `fluid_output`, `pattern`+`key`, …).
   Формы для литья (`consume_cast: false`, `*_mold`, `*_cast`), шаблоны смитинга и входы
   с `probability: 0` не считаются расходуемыми. Количества — `Fraction`, поэтому
   135 mB → 1.5 слитка считается точно, без ошибок float.

   Отдельные правила для форматов, которые иначе читаются молча и неверно:

   * `modern_industrialization:forge_hammer` — корневой `count` это **сколько предметов
     съедает** крафт (`3 raw → 4 dust`), а не количество выхода;
   * `quark:mixed_exclusion` — сетка 3×3 с пустым центром: 8 предметов тега, `placeholder`
     только для JEI и в расход не идёт;
   * шанс может стоять рядом с вложенной ссылкой, а не в ней (`enderio:sag_milling`,
     `immersiveengineering:crusher` → `secondaries`), иначе 1 + 1 = 2 выхода вместо
     1 + 0.33…0.35;
   * бонусные выходы под своими ключами (`itembi`/`fluidbi`/`gasbi`, `secondary_output` +
     братский `secondary_chance`, `fluid_outputs`) — неизвестный ключ по умолчанию считается
     **входом**, из-за чего бонус превращался в расход и рождал циклы с профитом в миллионы;
   * `catalyst` (draconicevolution fusion) — катализатор, а не вход.

   Санитарная проверка: цикл с профитом > 1000 или дефицитом > 100 000 помечается флагами
   `huge_profit` / `huge_deficit` и выводится с «⚠» — такие числа означают ошибку разбора,
   а не находку.
3. **Граф.** Ресурс = (`item` | `fluid` | `chemical`, id). Тег разворачивается в своих
   членов; крупные «категорийные» теги (`minecraft:wooden_doors` — больше тысячи членов)
   схлопываются в одного представителя, иначе граф превращается в один сплошной SCC из
   1:1-связей.
4. **Поиск.** Перебор простых циклов длины ≤ `--depth` — только внутри компонент сильной
   связности и только с произведением коэффициентов ≥ `--min-profit`. Каждый цикл
   перечисляется один раз (канонический старт).
5. **Точная проверка.** Для кандидата считаются кратности рецептов на `Fraction` и полный
   баланс по всем затронутым ресурсам. Расход ресурса за крафт — это **сумма всех записей
   рецепта, которые в него резолвятся**: и прямого id, и тегов, где он состоит
   (`8× #c:tiny_dusts/coal + 1× coal_tiny_dust` = 9 за крафт, а не 1). Дюп = стартовый
   ресурс в плюсе, остальные ≥ 0. Если чего-то не хватает, цикл уходит в «открытые» с
   указанием дефицита и рецепта, который его производит.
6. **Свёртка дублей** (см. выше) — в основную таблицу попадают только ядра.
7. **LP-проверка (`--prove`).** Ищется строго положительный вектор цен, при котором ни один
   рецепт не прибылен: найден → дюпов нет вообще, не найден → дюпы есть. Это доказательство
   полноты для релаксированной модели (теги смоделированы как общий узел цены).

## Производительность и кэш

На отладочной сборке (~72 000 файлов рецептов, ~43 500 ресурсов в графе, ~250 000 дуг):

* холодный прогон — разбор всех файлов плюс построение графа: порядка 5 минут
  (многое зависит от диска);
* повторный, с кэшем — около **15 секунд** при `--depth 4`;
* `--depth 5` — перебор циклов растёт на порядок.

Кэш лежит в `<--out>/cache/` и привязан к пути экспорта: если папку `export` перенесли или
обновили, первый прогон будет холодным. Сбросить кэш — `--no-cache` или удалить `out/cache/`.

## Тесты

```bash
python -m unittest discover -s tests -t . -v
```

* Синтетические тесты (мини-сборка с известным дюпом, катализаторы, шансы, LP-детектор,
  свёртка вариантов) работают всегда и данных не требуют.
* Интеграционные проверки требуют настоящего экспорта: переменная окружения
  `KUBEJS_DUPES_EXPORT=/путь/к/export` или папка `export/` рядом с репозиторием. Без экспорта
  они пропускаются. Часть из них — регресс на конкретной сборке (сталь ×3, медь ×1.5):
  если таких рецептов в вашем экспорте нет, проверка тоже корректно пропускается.

## Ограничения

* Ловятся **цепочные** циклы (каждый шаг — один ресурс → один ресурс). Ветвящиеся дюпы
  (рецепт с двумя входами, оба надо произвести из стартового ресурса) не ищутся.
* `--depth 5+` резко дороже: перебор растёт как степень ветвления графа.
* Гейтинг по стадиям и модам не моделируется — в отчёте видно мод и машину каждого шага,
  доступность оценивайте сами.
* При `--tags primary` и при схлопывании крупных тегов возможны артефакты подстановки:
  в отчёте они помечены `tag_primary`.
* **Экспорт — это сырой JSON датапака, а не то, что мод реально прочитал.** Если кодек мода не знает
  поле, оно молча исчезает, и рецепт работает иначе, чем написано в файле. Проверенный случай:
  у `oritech` вход — `List<Ingredient>`, **одна запись = один предмет**. Это архитектурное решение мода,
  а не баг: количество задаётся повтором записи (так пишет и их собственный датаген; в ветке `26.1`
  это прямо задокументировано — «each ingredient entry consumes one item… including repeated
  ingredients»), а `OritechRecipeBuilder` вообще не имеет перегрузки «вход + количество».
  Поэтому `{"tag": "c:dusts/steel", "count": 5}` — это «1 пыль». Такие типы перечислены в
  `normalize.py:INPUT_COUNT_IGNORED_PREFIXES`. Перед тем как верить количеству в новом типе рецепта,
  сверьтесь с кодеком мода.

## Структура репозитория

```
kubejs_dupes/
  cli.py         разбор аргументов и порядок этапов
  loader.py      обход recipes/, errors.log, кэш нормализации
  resources.py   реестры предметов/жидкостей и теги экспорта
  normalize.py   приведение рецептов к единому виду
  graph.py       граф ресурсов, рёбра-конверсии, SCC (Тарьян)
  search.py      перебор циклов, точная проверка, свёртка дублей
  verify.py      баланс ресурсов на Fraction
  report.py      отчёты markdown/json
  prove.py       LP-проверка полноты (scipy, опционально)
tests/
  test_examples.py  синтетические тесты + интеграционные на реальном экспорте
```
